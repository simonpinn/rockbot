# Reflex Tools

## Problem

A validated `SkillResource` — a wisp a subagent converged on and that has since succeeded three times across distinct sessions (`design/skill-asset-promotion.md`) — is fully trusted, but it is still *data*. Calling it means fetching the skill, finding the resource, and explicitly dispatching it through `spawn_wisps`. No agent can call it the way it calls a real tool: by name, with a schema, without first knowing which skill it lives under.

The cost of that gap compounds with use. Every call to a validated wisp still pays for the fetch-and-dispatch dance, and — more importantly — every call to a skill that *hasn't yet* been promoted pays the full cost of an LLM re-deriving a tool-call sequence it has already proven correct dozens of times. The pattern is structurally identical to the asymmetry `skill-asset-promotion.md` already names: a working pattern exists, but nothing makes it cheap to reuse. That document solved "capture the pattern." This one solves "make the captured pattern directly callable."

A second, related gap: `skill-asset-promotion.md` Phase 5 treats a failing provisional resource as disposable — two consecutive failures and it is deleted. That is the wrong response once a resource is directly callable with no LLM in the loop to notice and compensate for a bad call. RockBot already has a closed-loop repair mechanism (`design/self-repair.md`) built for exactly this shape of problem — diagnose, apply a correction, verify, escalate only after repeated failure — and it already has an applier for skill resources specifically (`SkillResourceApplier`, `RepairTarget.SkillResource`). It is simply not wired to this failure path yet.

## Goals

- A validated, `Wisp`-typed skill resource is callable as a first-class tool — discoverable, schema'd, zero LLM cost to replay — without changing how wisps execute or are sandboxed.
- A resource that stops being callable (demoted or deleted) is unregistered and evicted from every session holding it, with no stale tool left in anyone's list.
- A resource that starts failing is retrained before it is deleted: a corrected or re-earned version gets a chance to prove itself again, through the repair mechanism that already exists for this.
- Deletion is the last resort — it happens only after retraining has itself failed repeatedly, not on the first or second bad call.
- Tool registration stays cheap: a growing number of validated resources does not blow out every agent's tool list, the way an all-eager MCP typed-tool surface already proved it would.

## Non-goals

- Changing wisp execution, sandboxing, or process isolation. Only the calling convention changes — direct named call instead of fetch-then-spawn. Replay runs through the same wisp runner, unchanged.
- Eliminating the fetch-then-spawn path. It stays as the fallback whenever a resource has no registered tool (not yet validated, or mid-retraining).
- Covering `Python`-typed resources in Phases 1–3. A wisp replays calls through already-trusted executors; a promoted script is sandboxed code whose exposure changes meaningfully once it is callable from anywhere, not just via a subagent's explicit decision to run it. Addressed in Phase 4 below, once Phases 1–3 are proven on wisps.
- Running promoted code outside the existing container sandbox. Considered and rejected during Phase 4 design: compiling and loading C# via Roslyn in-process (`CSharpScript`/`AssemblyLoadContext`) provides *no* built-in sandboxing — no memory/CPU limits, no filesystem/network restriction — and would run with the full privileges of the host process, the opposite of CLAUDE.md's "process isolation so LLM-generated code cannot access the host directly." Matching what `ContainerScriptRunner` already gives Python for free (non-root pod, read-only FS, cgroup limits, deadline timeout) would require wrapping compiled C# in its own container anyway, at which point the isolation story is identical and a language change buys nothing. Python stays the only sandboxed-code resource type; nothing about the runtime changes in Phase 4.
- Unifying with `McpWrapperCatalog`/`McpTypedToolSurface` internals. That machinery fingerprints and reconnects a live downstream server connection; a reflex has none. `ReflexToolSurface`'s own LRU/pin bookkeeping stays a structurally identical, independent sibling — it does not reuse `McpTypedToolSurface`'s internal `Session` type or its `internal Evict`. The one unavoidable exception, forced by the host's own wiring rather than chosen here: only one `ITypedToolSurface` is resolved per run (see Phase 3), so a thin composite has to sit at that single seam — that's wiring, not an internals merge.
- Retroactively reflex-ifying resources deleted under the old demotion rule before this ships.

## Architecture overview

```
Skill store (validated, Wisp-typed SkillResource)
        │ polled each reconciliation cycle (no change-notification exists)
        ▼
 ReflexToolCatalog ──builds──> ToolRegistration + ReflexExecutor
        │                              │
        │ unregister on demote/delete  │ replays via the existing wisp runner
        ▼                              ▼
 ReflexToolSurface (session LRU + pin-the-owning-skill)
        │ wrapped, with McpTypedToolSurface, by one CompositeTypedToolSurface
        │ (the host resolves exactly one ITypedToolSurface per run)
        ▼
   Agent's tool list — callable by name, zero LLM replay cost

 Failure path (replaces "2 fails → delete"):
   ReflexExecutor failure ──feeds──> FailureClusterStore (existing)
        │
        ▼
   RepairTicket(Target=SkillResource)  [self-repair.md, already built]
        │  new directive decides the op, evidence-based:
        ├─ demote-provisional  (cause unknown — re-earn trust, no content change)
        ├─ attach               (cause evident — corrected content, re-earn trust)
        └─ after MaxAttempts (default 3) failed repair attempts → Escalated
                │
                ▼
          delete (real demotion — now the last resort, not the first response)
```

This design is additive on top of two already-shipped systems: `skill-asset-promotion.md`'s provisional/validated trust gradient, and `self-repair.md`'s ticket/apply/verify loop. Nothing here changes either system's own contract; it redirects one failure path in the first, and adds one new consumer (a new directive) that feeds the second.

## Phase 1 — Redirect the failure path through repair

### Where

`design/skill-asset-promotion.md` Phase 5 (Amendment 1, in that file) and `src/RockBot.Host/DreamService.cs` — specifically `RunProvisionalValidationPassAsync` (the provisional sweep, ~line 5523), `BuiltInRepairTicketCreationDirective` and `BuildRepairTicketCreationPrompt` (the repair-ticket proposal pass, ~lines 7883 and 8015).

### Change

Two independent fixes against real, already-traced code — no new directive file, no new DreamService pass:

1. **`RunProvisionalValidationPassAsync`'s `ProvisionalAction.Remove` case stops deleting directly, and its failure-recording bug gets fixed in the same change.** Today, on `Remove`, it calls `_skillStore.RemoveResourceAsync` immediately, then records a cluster via `_failureClusterStore.RecordAsync(clusterKey, sessionId: null, ...)` — purely as an after-the-fact note; `sessionId` is always `null`. Since `GetEscalatableAsync`'s threshold requires `SessionIds.Count >= 2` *distinct* ids, and `FileFailureClusterStore` only adds a session id to that set when it's non-empty, a cluster recorded this way can never reach `SessionIds.Count >= 2` — redirecting this path without also fixing the recording would leave the resource stuck forever, neither promoted, repaired, nor removed. The fix: stop calling `RemoveResourceAsync` (except as a fallback — see below); record using the real `SessionId` values already present on the recent failing `WispExecutionRecord`s in scope at this point in the loop (not `null`), using each record's own `ErrorMessage`/`FailedToolName` as the sample text instead of a generic constant string, and only recording failures genuinely newer than the cluster's existing `LastSeen` (a still-failing resource is re-swept every dream cycle with the same historical records otherwise, inflating `Count` and refreshing `LastSeen` on dream cadence alone — not real evidence). Once failures genuinely span two distinct sessions, the cluster crosses `GetEscalatableAsync`'s threshold on its own and the repair-ticket creation pass below picks it up. When the repair loop itself is unavailable (disabled, or a collaborator is missing — `DreamService.RepairLoopEnabled` false), fall back to the old direct `RemoveResourceAsync` behavior rather than leave the resource in permanent limbo with nothing to ever revisit it.
2. **The repair-ticket creation pass learns about `SkillResource`.** The apply/verify/escalate loop (`RunRepairTicketApplyAsync`) is already fully generic over `RepairTarget` — unchanged. `SkillResourceApplier` needed one fix, caught in review: `demote-provisional` flipped `Provisional` true→true with no other effect when the resource was *already* provisional — which is the only state this failure path can ever produce, since `RunProvisionalValidationPassAsync` only sweeps provisional resources. That made the op a silent no-op: the ticket resolved on the first cheap verify with nothing actually changed, and the pattern was then permanently excluded from future proposals (a prior ticket must be `Escalated`, not `Resolved`, to try again) — stuck forever, worse than the old delete-on-two-fails. The fix: `demote-provisional` always restamps `CreatedAt` to now, resetting the validation window, regardless of whether `Provisional` was already true — a real retraining action either way. Separately, upstream of the applier: `BuiltInRepairTicketCreationDirective`'s prompt text (both its prose target list *and* its strict output-schema enum — both needed the addition) lists four target types and not `SkillResource`, so the LLM never proposes one for a `server="skill-resource"` cluster. A fifth block teaches it: such a cluster's `tool` is the skill name and `errorClass` is the resource filename; the `Change` shape is `{skill, filename, op, content?, type?, description?, verifyHint?}` matching `SkillResourceApplier.SkillResourceChange` exactly; `op` is evidence-based — `demote-provisional` when no specific cause is known, `attach` with corrected content when one is (e.g. a fingerprint-drift note in the sample error messages), and `delete` only when the cluster's own prior-attempt history shows a previous ticket for this exact pattern already reached `Escalated`. That last case requires `BuildRepairTicketCreationPrompt` to carry prior-ticket history per cluster, which it does not natively (it shows count/sessions/sample errors, nothing about tickets already tried) — extended to include, per cluster, a one-line note of any prior ticket's `Target`/op and final `Status` for that pattern. The directive also needs explicit verify-shape guidance for `SkillResource`: there is no tool call that proves a `demote-provisional`/`attach` fix worked yet (the resource has to actually be used again first, on its own schedule), so the guidance is to pick any cheap, reliably-succeeding call purely so the ticket resolves — and, critically for `delete`, one *unrelated* to the resource just removed, since a failing verify auto-reverts the apply and would silently undo the deletion.

### Acceptance

- A provisional resource that would have been removed under the old rule is not removed; the cluster it produces has real, non-null, non-empty session ids and real error text, drawn from the failing wisp records, and does not keep growing when the same old failures are re-swept with no new activity.
- A `server="skill-resource"` cluster that crosses the escalation threshold gets a `RepairTicket(Target=SkillResource)` proposed, with `demote-provisional` chosen absent specific evidence and `attach`/`delete` chosen when prior-attempt history or sample errors justify it; `demote-provisional` has a real, verifiable effect (a restamped `CreatedAt`) even on an already-provisional resource.
- A resource is deleted only once its ticket reaches `Escalated` — and that requires the creation pass to see, from `BuildRepairTicketCreationPrompt`'s prior-attempt note, that retraining was already tried for this exact pattern — and a `delete` ticket's own verify must not depend on the resource it just removed, or a failing verify will auto-revert the deletion.
- If the repair loop is unavailable, the old direct-removal behavior still applies — no configuration leaves a failing provisional resource permanently un-repaired and un-removed.
- This phase ships value with zero reflex tools registered anywhere — every existing skill resource gets a retraining chance before deletion, independent of Phase 2.

## Phase 2 — `ReflexToolCatalog` and `ReflexExecutor` (Wisp-only)

### Where

New project `src/RockBot.Tools.Reflex/`, sibling to `src/RockBot.Tools.Mcp/` (one new `<Project Path="...">` line in `RockBot.slnx`). Also touches `src/RockBot.Wisp/SpawnWispsExecutor.cs` (extraction — see below) and `src/RockBot.Tools.Mcp/McpServerNames.cs` (reserved name).

### Change

The original sketch of this phase assumed several things that turned out not to exist when checked against the actual code — corrected here rather than discovered mid-implementation, the same way Phase 1's review caught `SkillResourceApplier` needing a real change instead of none:

- **Reconciliation is a timer, not a watch.** `ISkillStore` has no change-notification of any kind — there is nothing to "watch." `ReflexToolCatalog` is its own `IHostedService` running a periodic reconciliation loop. Each cycle: list all skills, scan manifests for validated (`Provisional=false`), `Wisp`-typed resources, diff against what's currently registered, `Register`/`Unregister` the delta — structurally the same diff-and-swap `McpWrapperCatalog` already does for MCP tools, just timer-triggered instead of triggered by its `McpServersIndexed` message. `WispToolRegistrar`/`DreamCostToolRegistrar` are *not* the precedent here despite the original wording — each registers one static tool exactly once, forever, and never reconciles a changing set. `McpWrapperCatalog` is the only existing precedent for dynamic multi-tool registration in this codebase, and this phase mirrors it.
- **No schema exists yet — reflexes ship as zero-argument tools in this phase.** `SkillResource` carries no parameter schema, and a wisp's steps are literal `JsonElement`s fixed at authoring time with no external input point. "Schema from the wisp's declared parameters" didn't correspond to anything real. `ToolRegistration.ParametersSchema` is an empty-object schema here — a reflex in this phase is a named, zero-argument replay of a fixed pipeline. Accepting caller-supplied parameters would mean extending the wisp step format itself; that's out of scope, the same boundary as the existing "not changing wisp execution" non-goal, not something this phase assumes.
- **Eviction moves to Phase 3 — there's nothing to evict from yet.** `McpTypedToolSurface.Evict` (the hook the original sketch said to reuse) removes tool names from a *session's* active/pinned list — but that per-session activation list is `ReflexToolSurface`, which doesn't exist until Phase 3. This phase cannot evict from a structure that isn't built yet. Scoped down: on demote/delete, `ReflexToolCatalog` only unregisters via `IToolRegistry.Unregister`. A registered reflex is visible to every session immediately (the same unscoped visibility `WispToolRegistrar`'s/`DreamCostToolRegistrar`'s tools already have) until Phase 3 wraps registration with session-level activation/pinning/eviction, without changing this phase's registration contract.
- **Replay reuses the runner, but the runner's logging path is private — it needs extracting, not just calling.** The `(skillName, filename, succeeded)`-shaped event Phase 1 depends on is actually a `WispExecutionRecord` appended via `IWispExecutionLog.AppendAsync`; building one (canonicalize → hash → circuit-breaker check → `WispExecutor.ExecuteAsync` → log) happens entirely inside `SpawnWispsExecutor`'s private `ExecuteOneAsync`/`LogExecutionAsync`. This phase extracts that pipeline into a method both `SpawnWispsExecutor` and the new `ReflexExecutor` call — a real change to an existing file, not a "reused as-is" dependency.
- **No lease/ref-count machinery — a cheaper pattern already fits.** `McpServerConnections`' lease pattern exists because a live server connection is a genuinely shared, disposable resource; nothing in `ReflexExecutor` is. `McpWrapperCatalog` gets the same "an in-flight call is immune to a concurrent registry change" guarantee for free, just by reading one immutable record out of a `volatile`-swapped dictionary at the start of a call and using that local copy for the rest of it. `ReflexExecutor` does the same — no lease, no release, no disposal.
- **No `via=reflex` tag — the existing name tag already disambiguates for free.** `via=wrapper|invoke_tool` lives only on `McpDiagnostics`' MCP-specific counter — not the right place for a reflex call regardless. The generic, cross-backend counter (`ToolDiagnostics.Invocations`/`InvokeDuration`, tagged today by `rockbot.tool.name`/`rockbot.tool.status` at four call sites across `AgentLoopRunner.cs` and `RockBotFunctionInvokingChatClient.cs`) has no source/backend tag, and adding one would mean injecting `IToolRegistry` into both of those classes — two of the most heavily used and heavily tested components in the host — just to resolve a tag already implied by the tool's own name. Every reflex tool's name already starts with `reflex__`, so cost analysis (the feature's original motivation) is a `rockbot.tool.name` prefix filter away, at zero new risk. Not worth the blast radius for what the prefix already gives for free; revisit only if a real dashboard need shows the prefix filter is insufficient.
- **Reserved-name enforcement has a confirmed home.** `McpServerNames.Validate` already rejects server names containing the `__` separator; this phase adds one more check there rejecting the literal name `"reflex"`, closing the one real collision risk (an MCP server named exactly `reflex` producing tool names that share reflex's own prefix).

### Acceptance

- A validated Wisp resource is registered as a callable tool within one reconciliation cycle; its schema takes no arguments.
- A demoted-to-provisional or deleted resource is unregistered from `IToolRegistry` within one reconciliation cycle. (Session-level eviction is Phase 3's acceptance criterion, not this phase's — there is no session activation list yet.)
- A direct reflex call still appends a `WispExecutionRecord` via the same path `spawn_wisps` uses, so Phase 1's repair/validation read-path sees it exactly as if it had gone through fetch-then-spawn.
- A reflex call's invocation appears in the generic tool-invocation metrics tagged `rockbot.tool.name=reflex__...` like any other registered tool — already filterable by name prefix, no new tag needed.
- A reconciliation cycle racing an in-flight call does not fail the call in progress — it completes against the snapshot it started with.
- An MCP server cannot be registered with the literal name `reflex`.

## Phase 3 — `ReflexToolSurface` (lazy activation, pin-the-owning-skill)

### Where

New file(s) in `src/RockBot.Tools.Reflex/`, sibling to `McpTypedToolSurface` (`src/RockBot.Tools.Mcp/McpTypedToolSurface.cs`) in structure, not in interface — see Change. Also touches `src/RockBot.Agent/Program.cs` (composite wiring) and `src/RockBot.Host/AgentContextBuilder.cs` (the skill-recall pin-on-touch call, ~lines 308 and 626-693).

### Change

The original sketch assumed `ReflexToolSurface` could be a true independent sibling `ITypedToolSurface`, the same way `ReflexToolCatalog` is an independent sibling of `McpWrapperCatalog`. Checked against the actual code, that's not available: `ITypedToolSurface` (`src/RockBot.Host/TypedToolSurface.cs`) is resolved as exactly one DI singleton and held in exactly one `AsyncLocal` slot per run (`TypedToolSurfaceContext`, same file), set once by `AgentLoopRunner.RunAsync` and consumed by one `TypedToolSurfaceChatClient` in the pipeline. There is no second slot for a second surface to occupy. (Checked and confirmed separately: MCP's own typed/lazy/pinned surface is not dormant — `AddMcpToolProxy`, called unconditionally from `src/RockBot.Agent/Program.cs:385`, already registers `ITypedToolSurface`/`McpTypedToolSurface`/`McpWrapperCatalog` for real, running in `Pinned` mode per the deployed Helm default `McpBridge__WrapperMode=Pinned`. An earlier pass at this research mis-attributed that registration to a different, genuinely-unused method of a similar name, `AddMcpTools` — corrected here before it reached a task.) Corrections:

- **A `CompositeTypedToolSurface : ITypedToolSurface`** (new, `src/RockBot.Tools.Reflex/`) takes a required `McpTypedToolSurface` and the new `ReflexToolSurface` and wraps both. It is registered in `src/RockBot.Agent/Program.cs`, *after* the existing `agent.AddMcpToolProxy(...)` and `agent.AddReflexTools(...)` calls, as one more `AddSingleton<ITypedToolSurface>(...)` — the last registration of a service type wins on resolution, so this one supersedes `AddMcpToolProxy`'s own `AddSingleton<ITypedToolSurface>(sp => sp.GetRequiredService<McpTypedToolSurface>())` (`McpServiceCollectionExtensions.cs:112`) without touching that file. `ModeFor`, `LoaderToolName`, `Orientation`, and `MaxToolsPerRequest` all delegate straight to the wrapped `McpTypedToolSurface` — reflex mirrors whatever mode MCP's own `McpBridge:WrapperMode` config resolves to per tier (Pinned, today), rather than carrying a second, independently-configured mode that could disagree with it over the one ambient slot both surfaces share. `IsTypedTool`, `GetActivated`, and `ActivateByName` delegate to *both* inner surfaces (union/first-match) — those decide which tool names apply, not which mode governs them. `ReflexToolSurface` itself does **not** implement `ITypedToolSurface` — it's a plain class the composite delegates to, exactly the shape `McpTypedToolSurface` already has internally (own `Session` type, own LRU/pin bookkeeping, own idle sweep), just not wearing the interface directly. This is wiring forced by the host's single-slot design, not an internals merge with MCP's machinery — the two surfaces' bookkeeping stays separate.
- **Per-session LRU activation list**, bounded at 40 (matching `McpToolSurfaceOptions.MaxActivatedToolsPerSession`, `src/RockBot.Tools.Mcp/McpToolSurfaceOptions.cs:67`), where re-using a reflex keeps its place instead of resetting it — independent of MCP's own budget (different surface, and sharing slots risks one starving the other). Mirrors `McpTypedToolSurface`'s idle-sweep behavior too: an `ActivationIdleTimeout` (12h, matching `McpToolSurfaceOptions.cs:72`) with a periodic sweep (10-minute timer, matching `McpTypedToolSurface`'s own) clearing sessions idle past it — `ReflexToolSurface`'s state is in-memory only, same as MCP's, not persisted across host restarts.
- **Pin-the-owning-skill, not "namespace pinning."** There is no hierarchical skill-namespace type in this codebase — `Skill` (`src/RockBot.Host.Abstractions/Skill.cs:38`) has a flat `string Name` and no grouping field; a slash in a skill name (e.g. `"calendar/scan"`) is convention, not structure. The real, already-existing grouping unit is the skill itself: `ReflexToolSurface.Pin(sessionId, skillName)` pins every one of that skill's currently-*registered* reflex tool names, read live from `IReflexRegistrationLookup.GetToolNames(skillName)` (a reverse index added to that interface this phase) rather than from the skill's raw `Manifest` via `ISkillStore` — this way a demoted resource that no longer has a reflex tool is never pinned, with no separate existence check needed. Bounded by a separate small cap — 3, matching `McpToolSurfaceOptions.MaxPinnedServersPerSession`, `McpToolSurfaceOptions.cs:53`. The "touch" that triggers a pin is skill recall surfacing the skill (see below) — calling a reflex tool directly by name (`ActivateByName`) activates only that one tool in the session's LRU list; it does not also pin the rest of its owning skill, unlike MCP's own call-pins-the-server behavior. Kept this way deliberately: Phase 3's one real-world trigger for "entering the activity" is recall, and adding a second, call-triggered pin path was not needed to make it work — revisit if usage shows the asymmetry matters.
- **Discovery is automatic context injection, not a tool call.** Skill recall is not `mcp_find_tools`'s kind of loader tool — it's unconditional per-turn injection in `AgentContextBuilder.cs` (`skillStore.SearchAsync(...)`, ~line 308, rendered into context ~lines 634-693), already running with `sessionId` in scope. The pin-on-touch trigger hooks directly there: every BM25-recalled skill this turn (not only the ones newly marked for full-body injection — a skill must be re-touched on every turn it's recalled, or it can never be reached again once evicted from the pin cap by a later pin) gets `reflexHooks?.OnSkillSurfaced(wmNamespace, skill.Name)` called synchronously, in reverse rank order so the best-ranked match is pinned last and survives the cap when a turn recalls more skills than it can hold. Pinned under `wmNamespace` (`workingMemoryNamespace ?? $"session/{sessionId}"`, and the worker builder's own `workingMemoryNamespace` parameter) — the id the loader tool and every other registry tool actually carry as their `ISessionBoundTool.SessionId` — not the raw `sessionId` parameter, which is a different string on every call path except `ScheduledTaskHandler` and which `GetActivated` is never actually queried with. (Caught by a fresh-context review after the first implementation pass keyed pins by the raw `sessionId`, which made recall-driven pinning a no-op in production for user, subagent, and worker runs; see the ledger's Critical #1 fix.) The later join into `ChatOptions.Tools` still goes through the composite surface and `AddActivated`, same as MCP's own tools. The existing `SkillTools.FormatResourceTag` (`src/RockBot.Skills/SkillTools.cs:438`), which already renders `[Wisp, Python]`/`[Wisp*]` manifest tags into the skill index the LLM sees, is the existing extension point for showing a resource as directly callable — not new discovery UI. That index is built once per session (`skillIndexTracker.TryMarkAsInjected`), from whichever resources are already registered reflex tools at that moment — a resource validated later in the same session never gets added to it retroactively; the resource is still directly callable once the model learns its name some other way (recall, memory, a prior turn), just not re-advertised in the one-time index text.
- **`TryGetLoader`'s exact-name match is a deliberate gate, not relaxed.** The original sketch read `TypedToolSurfaceContext.TryGetLoader` (`TypedToolSurface.cs:201-221`) requiring the *specific* tool named `surface.LoaderToolName` (`"mcp_find_tools"`) — not just any `ISessionBoundTool` — as an incidental implementation detail worth loosening so Reflex activation wouldn't depend on an MCP-specific tool being present. Checked against the test suite, it is not incidental: `McpLazyTypedToolsTests.AddActivated_RunWithoutTheLoaderTool_GetsNothing` asserts, by name, that "a tool profile without `mcp_find_tools` must not gain typed tools" even when another session-bound registry tool (`mcp_invoke_tool`) is present in the same list. `mcp_find_tools`'s presence is the deliberate, already-tested per-profile opt-in signal for *all* typed-tool activation, lazy or pinned — a boundary this phase should extend to reflex tools via the composite, not route around. No change to `TypedToolSurface.cs`; a profile that excludes `mcp_find_tools` correctly gets no reflex activation either, exactly as it gets no MCP typed-tool activation today.
- **Reflex is exempt from `IsTypedTool` on an `Off` tier.** `TypedToolSurfaceContext.Shape` drops any name `IsTypedTool` claims whenever the run's mode isn't `Eager` — including `Off`, which (unlike Lazy/Pinned) never runs `AddActivated`/`TryActivate` to bring anything back, and reflex has no `mcp_invoke_tool`-style generic fallback the way MCP tools do. Composite's `IsTypedTool` checks `TypedToolSurfaceContext.Mode != TypedToolMode.Off` before consulting `reflex.IsReflexTool`, so a reflex tool stays in the base/eager list on an `Off` tier exactly as it was in Phase 2, while still being Lazy/Pinned-gated on every tier that actually activates typed tools. (Also caught by the fresh-context review; without this, any tier configured `Off` would have silently lost every reflex tool with no way to get them back.)
- **Its own `Evict`, not a reused one.** `McpTypedToolSurface.Evict` (`McpTypedToolSurface.cs:315`) is `internal` and operates on MCP's own `_sessions` dictionary — not reusable. `ReflexToolSurface` gets a structurally identical `Evict(IReadOnlySet<string> toolNames)`, called directly by `ReflexToolCatalog`'s existing reconciliation loop at the same point it calls `IToolRegistry.Unregister` for a demoted/deleted resource — so a stale reflex tool is both unregistered globally and dropped from every session's active/pinned list in the same reconciliation cycle.

### Acceptance

- Skill recall pins every currently-registered reflex tool of the recalled skill into the triggering session's list, under the session's real tool-session id (not the raw `sessionId`), bounded and LRU-evicted at the pin cap (3); a still-relevant skill is re-pinned on every turn it's recalled, not only the first.
- Re-activating a reflex keeps its place in the session's LRU list rather than resetting it; the list is bounded at 40 and idle-swept after 12h, mirroring `McpTypedToolSurface` exactly.
- Skill-recall context injection that surfaces a skill with validated reflexes pins them into the triggering session and renders them as directly callable in the skill index text (for resources already registered at the moment the once-per-session index is built).
- A demoted/deleted resource is evicted from every session's active/pinned list within the same reconciliation cycle that unregisters it from `IToolRegistry` — no session is left holding a stale reflex tool name.
- A tool profile that excludes `mcp_find_tools` gets no reflex activation either — the same deliberate per-profile gate that already withholds MCP's own typed-tool activation.
- A tier configured `Off` still has every reflex tool in its base tool list — Off only ever strips typed tools and never re-adds them, so reflex is exempted from `IsTypedTool` in that mode rather than silently losing them with no fallback.
- `CompositeTypedToolSurface` correctly delegates `IsTypedTool`/shaping/`AddActivated` to both inner surfaces with no behavior change to MCP's own existing typed-tool-surface tests.

## Phase 4 — Python-typed reflexes: a fixed trust signal, a stricter bar, and a human override

### Where

`src/RockBot.Host/DreamService.cs` (`RunProvisionalValidationPassAsync`, `DecideProvisionalAction`, ~lines 5523–5795), `src/RockBot.Scripts.Remote/ScriptToolExecutor.cs` and its `.csproj`, `src/RockBot.Tools.Reflex/ReflexToolCatalog.cs`, `ReflexExecutor.cs`, `ReflexOptions.cs` and its `.csproj`, `src/RockBot.Host.Abstractions/SkillResource.cs`, `src/RockBot.Skills/SkillTools.cs`, and the handler that owns the one genuine live-user-chat-turn `SkillTools` construction site (`src/RockBot.Agent/UserMessageHandler.cs:238`).

### Change

Investigation while scoping this phase found the open question from the original sketch ("should the trust bar be higher for Python?") was premature — Python resources don't have a real trust signal to set a bar against yet at all. Three changes, in dependency order:

**4a. Fix Python's promotion signal — a real bug, independent of reflexes.** Today, `DecideProvisionalAction` (`DreamService.cs:5736`) promotes a `Wisp` resource by cross-referencing `SkillResource.DefinitionHash`/wisp `ShapeHash` against real `WispExecutionRecord.Succeeded` outcomes. For every other resource type, including `Python`, it unconditionally overrides that count with `ISkillResourceUsageStore.QueryCheckoutsAsync` — a **fetch** event, recorded whenever `GetSkill` reads the resource (`SkillTools.cs:166-173`), not an execution outcome. A Python script promotes to validated after being *read* three times across sessions, whether it ever ran, or ran and failed every time — and because `DecideProvisionalAction`'s failure/removal rule only ever consults `wispRecords`, a failing Python resource can never be flagged for repair either; it just sits provisional forever. `ISkillResourceUsageStore`'s own doc comment already names checkouts as "the fallback for Python scripts... whose success/failure can't be cross-referenced" — the gap was known, just never closed.

The fix reuses the existing cross-reference instead of building a parallel one: `ScriptToolExecutor.ExecuteAsync` (`RockBot.Scripts.Remote`) already has everything a `WispExecutionRecord` needs in scope after calling `runner.ExecuteAsync` — `request.SessionId` (from the inbound `ToolInvokeRequest`), the script text, and `response.IsSuccess`/`ExitCode`/`Stderr`. It appends a `WispExecutionRecord` via a newly-injected `IWispExecutionLog?` (same fire-and-forget try/catch convention `ReflexExecutor`/`SpawnWispsExecutor` already use), with `DefinitionHash` = the same SHA-256-hex16 scheme `SkillTools.ComputeContentHash` uses on the script text, `ShapeHash = null` (Python gets no shape-tolerant matching in this phase — see Risks), `StepCount = 1`, `StepsCompleted = response.IsSuccess ? 1 : 0`, `FailedStepId/Index/ToolName = null`, `ErrorMessage` from `response.Stderr`/exit code. This requires one new `ProjectReference` to `RockBot.Host.Abstractions` in `RockBot.Scripts.Remote.csproj` (a leaf abstractions project; no cycle — `RockBot.Host.Abstractions` has no reference back).

`RunProvisionalValidationPassAsync`'s query at `DreamService.cs:5557` already matches on `DefinitionHash` alone, with no `resource.Type == Wisp` gate — so a Python resource whose executions now land in `IWispExecutionLog` is already found by the existing query with zero changes there. The only change needed in `DecideProvisionalAction` (`DreamService.cs:5766`): stop *unconditionally* discarding `wispRecords`-based counting for every non-Wisp type. New rule: use `wispRecords` (now real for `Python` too) whenever any exist for this resource; fall back to the checkout-based soft signal only when `wispRecords.Count == 0` — preserving the fallback for `JsonSchema`/`Markdown`/`Text`/`Other`, which have no execution concept and never will. This one change makes Python's promotion *and* its failure/repair-flagging symmetric with Wisp's, through machinery Phase 1 already built generically.

**4b. `ReflexToolCatalog`/`ReflexExecutor` extended to `Python`, gated above the base bar.** `ReflexToolCatalog.ReconcileOnceAsync` additionally scans `SkillResourceType.Python` resources with `Provisional=false` — which, after 4a, correctly means "really succeeded `ProvisionalSuccessThreshold` times across distinct sessions," the same guarantee Wisp already carries. Registering as a *reflex* — zero-deliberation, callable with no LLM in the loop to notice a bad call — is a strictly higher bar for sandboxed code than for a replay of already-trusted tool calls: a new `ReflexOptions.MinPythonSuccessesBeforeReflex` (default 5, configurable) must also be met, checked against the count of successful `IWispExecutionLog` records matching the resource's `DefinitionHash` — the same records 4a now produces, no new store. Wisp keeps no extra gate (its validation bar already is its reflex bar, unchanged from Phase 2). `ReflexExecutor` gets a second branch: for a `Python` lookup, fetch the resource's current script body fresh (mirroring the Wisp branch's fresh-fetch-every-call pattern), execute it via the same `IScriptRunner` the `execute_python_script` tool already resolves (a new `ProjectReference` to `RockBot.Scripts.Abstractions` in `RockBot.Tools.Reflex.csproj`; whichever `IScriptRunner` is DI-registered — local or the bus-mediated remote proxy — is used transparently, same as `execute_python_script` itself), and append the same 4a-shaped outcome record before returning.

**4c. A human-requested trial-and-validate override — new capability, not in the original sketch.** Resolved during design: a higher automatic bar is right, but a live human explicitly asking for a specific resource to be trusted now is a stronger signal than any count, provided it's backed by a real, witnessed success rather than taken on faith. New `SkillTools` constructor parameter `bool enableManualReflexPromotion = false`, passed `true` only from the `SkillTools` construction inside `UserMessageHandler.cs:238` — the one call site that is unambiguously a live user chat turn, never from `SubagentRunner`, `ScheduledTaskHandler`, or the A2A handlers. (Whether `UserFeedbackHandler`/`McpQuestionAnswerHandler` also qualify — they handle a human's reply mid-flow, which may or may not count as "asked for this directly" — is confirmed by reading each handler's role during implementation, not asserted here.) Mirrors the existing `enablePromote`/`PromoteSkillAsset` gating exactly (`SkillTools.cs:44,81`).

Gated by that flag, a new tool `RequestReflexTrial(skillName, filename)`: looks up the named resource (any type, must already exist on the given skill), runs it exactly once through the real execution path (`WispReplayPipeline` for `Wisp`, `IScriptRunner` for `Python` — the same paths 4a/4b use), and appends the same outcome record either way. On success: immediately sets `Provisional: false`, bypassing both the normal statistical gate and Python's extra 4b bar — tagged with a new `SkillResource.PromotedBy` field (`string?`, default `null`; set to `"user-request"` here) so a human-fast-tracked resource stays distinguishable in the manifest from a statistically-earned one, though it is subject to the exact same post-hoc repair/demotion safety net afterward regardless of how it got there. On failure: the resource is left exactly as it was; the failure is reported back in the same turn so the human sees it immediately, and — because the outcome was still recorded — a failing trial legitimately counts toward the normal failure-threshold/repair-flagging path rather than being thrown away. The tool's `[Description]` must say plainly that this runs the resource for real, with real side effects, the same way `PromoteSkillAsset`'s own description already carries explicit behavioral instruction — so the LLM confirms with the human before invoking it rather than firing it on a passing remark.

### Acceptance

- A Python resource that is only ever fetched, never successfully run, does not promote — `Provisional` stays `true` indefinitely rather than flipping after three reads.
- A Python resource that runs and fails repeatedly gets flagged into the Phase 1 repair-ticket path exactly as a failing Wisp already does, with no new wiring beyond 4a's signal fix.
- A Python resource that genuinely succeeds `ProvisionalSuccessThreshold` times across distinct sessions promotes (`Provisional: false`) exactly as a Wisp does today.
- A validated (`Provisional=false`) Python resource is registered as a reflex tool only once its successful-execution count (from the same records) also clears `ReflexOptions.MinPythonSuccessesBeforeReflex`; a Wisp needs no additional count beyond validation.
- A direct Python reflex call executes the resource's current stored script through the same `IScriptRunner`/container sandbox `execute_python_script` already uses, and appends an outcome record visible to the same validation/repair read-path.
- `RequestReflexTrial` is callable only when `enableManualReflexPromotion` is true, i.e. only from a genuine live user chat turn — never from a subagent or scheduled task.
- A successful `RequestReflexTrial` call immediately validates the named resource, tagged `PromotedBy: "user-request"`, regardless of its prior success count; a failed call leaves the resource unchanged but still records the attempt.
- No Roslyn/C#-scripting infrastructure is introduced; `Python` remains the only sandboxed-code resource type, running through the unchanged `ContainerScriptRunner`/`LocalScriptRunner` isolation.

## Risks and open questions

- **Repair-pass misjudgment.** The new directive could pick `attach` with content that's still wrong, or `demote-provisional` repeatedly on a cause `attach` would have fixed faster. Mitigation: `RepairTicket`'s existing attempt/verify loop already bounds this — a wrong choice just consumes one of `MaxAttempts` before escalating.
- **Pin granularity.** A skill's manifest can hold more validated Wisp resources than the pin cap fits in one step (3). Mitigation: the activation budget (40) caps the total regardless of how a single skill's pin fills it; revisit the pin-count default (3) empirically once real usage data exists, the way `worker-subagents.md` treats its own defaults.
- **Single ambient `ITypedToolSurface` slot.** The host resolves exactly one `ITypedToolSurface` per run (`TypedToolSurfaceContext`), so `ReflexToolSurface` cannot be a true independent sibling the way `ReflexToolCatalog` is to `McpWrapperCatalog` — it needs a `CompositeTypedToolSurface` wrapping both. Mitigation: the composite is a thin delegator with no shared state between the two inner surfaces, so this is a wiring constraint, not a design coupling; a bug in one surface's bookkeeping can't corrupt the other's.
- **Two independent LRU/pin systems to reason about** (MCP's and reflexes'). Mitigation: kept deliberately structurally identical so the mental model transfers directly; revisit merging only if usage shows no cross-pressure risk.
- **Reserved-word collision.** `"reflex"` as a reserved MCP-server-name prefix needs enforcement at server registration time, not just at reflex-tool naming time, or a future `mcp_register_server` call could create an ambiguous name.
- **Zero-argument-only reflexes.** Phase 2 ships reflexes that take no arguments (no schema exists today to do otherwise — see Phase 2's "Change"). A fixed, parameterless replay is still real value for the patterns that fit it, but it undersells what "callable tool" suggests to a reader expecting arguments. Parameterizing reflexes would mean extending the wisp step format itself — a genuinely separate, larger change, not assumed here.
- **Python gets exact-match hashing only, not shape tolerance.** Wisp resources match across cosmetically-different-but-structurally-same executions via `ShapeHash` (Phase 2's `WispReplayPipeline.ComputeShapeHash`, which strips literal values and prompt text). Phase 4 gives Python only exact-content-hash matching (`DefinitionHash`) — a subagent that re-derives "the same" script with different variable names or literal values starts a fresh count rather than adding to an existing one. This is a real limitation, not an oversight: an AST-normalized or otherwise literal-insensitive hash for Python is a genuinely separate, harder problem (Python has no equivalent of a wisp's already-structured step list to hash selectively) and is deliberately deferred rather than solved here. The real execution-outcome signal 4a adds is still a strict improvement over today's fetch-counting even without shape tolerance.
- **The human-override path (4c) is a new trust lever, not infrastructure reuse.** `RequestReflexTrial` lets one witnessed success — on a live human's explicit say-so — immediately clear both the normal statistical gate and Python's extra reflex bar. The mitigation is the same one `RepairTicket`'s loop already relies on elsewhere: a resource fast-tracked this way is subject to the identical post-hoc failure-clustering/repair-ticket/escalation path as any other validated resource if it turns out to misbehave, so a wrong human call is bounded by the same safety net, not exempt from it. The gating flag (`enableManualReflexPromotion`) must be wired only from a call site that is genuinely a live user chat turn — confirming that for every candidate handler (not just `UserMessageHandler`) is implementation-time due diligence, not a design-level guarantee this document can make on its own.

## Migration

- No migration required for existing skills, memory, or wisps for Phases 1–3. `SkillResource`'s schema is unchanged; `Provisional`, `CreatedAt`, and the manifest shape already carry what Phase 2 needs to read.
- Phase 4 adds one new optional field, `SkillResource.PromotedBy` (`string?`, default `null`). Additive with a default — per this repo's own convention (CLAUDE.md, "Persisted store schemas"), the tolerant deserializer absorbs it with no store-version bump and no `ISchemaMigration`.
- `RepairTarget.SkillResource` and `SkillResourceApplier` already exist and are unchanged by this work; only the trigger path into them changes (Phase 1).
- Resources already deleted under the old two-strikes rule are not retroactively restored.
- Existing Python resources already sitting `Provisional=false` under the old fetch-count rule are not retroactively re-validated or demoted by Phase 4 — the fixed signal only governs resources that pass through the pass after this ships.
